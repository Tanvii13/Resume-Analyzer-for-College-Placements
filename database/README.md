# Resume Analyzer — Sprint 1 Database

Small, editable PostgreSQL schema for US-01 to US-04:
- US-01: account data and role mapping
- US-02: uploaded resume metadata
- US-03: parsed resume sections
- US-04: processing status and readable error message

## Run it

1. Make sure PostgreSQL 18 is running and the `resume_analyzer` database exists.
2. Open pgAdmin Query Tool for `resume_analyzer`, or use `psql`.
3. Run `schema.sql`.

Using terminal:

```bash
psql -U postgres -d resume_analyzer -f database/schema.sql
```

If your PostgreSQL username is not `postgres`, replace it with yours.

## Important design choices

- The PDF/DOCX file itself is stored in private file storage, NOT inside PostgreSQL.
  `storage_key` points to that file; coordinate the exact storage-key format with the backend team.
- Never store plain-text passwords. `password_hash` must contain a secure hash generated by the authentication/backend layer.
- `resume_sections` stores parsed sections such as `education`, `skills`, `projects`, and `experience`.
- `resumes.status` plus `error_message` lets the app report invalid/unreadable files.
- UUID keys, UTC-aware timestamps (`TIMESTAMPTZ`), foreign keys, checks, and indexes are included.
- The schema uses `CREATE TABLE IF NOT EXISTS` and inserts default roles safely on rerun. Note: if tables already exist, rerunning this file does not automatically modify their existing columns or constraints; use a migration for changes to an existing database.
- Resume file size must be greater than 0 and at most
  5 MiB (5,242,880 bytes), enforced by database constraints.

## Sprint 2

Add new tables in a separate migration/script, for example `skills`, `resume_skills`, `analyses`, and `score_components`. Do not put them into this Sprint 1 file yet. Link those tables to `resumes.id` so the existing schema remains compatible.

## Before backend integration

Agree with the backend team on:
1. `storage_key` format and allowed file types/size limits.
2. The exact list of roles they will use.
3. The section names the parser will produce.
4. Who updates `status`, `error_message`, and `processed_at`.

This folder contains database code only; it does not implement backend APIs or file parsing.
